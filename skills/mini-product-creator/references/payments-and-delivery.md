# Оплата и автоматическая выдача

Читай перед реализацией покупки, webhook/callback, прав доступа и выдачи. Цель: **человек купил именно обещанный товар, получил его и может воспользоваться**. Наличие кнопки оплаты этого не подтверждает.

## Выбери один подходящий маршрут

Уточняй только неизвестное: что продаём, где оформляют покупку, куда выдаём, есть ли аккаунт продавца/платформа, один платёж или пакет/срок. По умолчанию для мини-продукта нужна разовая покупка. Не подключай обе кассы и подписку без причины.

| Ситуация | Подход |
| --- | --- |
| PDF/видео через подходящую готовую платформу | Предпочти её встроенные оплату и закрытую выдачу, если они выполняют условия продукта и проверяются |
| Самостоятельный сайт с цифровым товаром | Подходящая ЮKassa/Prodamus, серверная проверка, защищённая выдача |
| Цифровой товар/доступ продаётся внутри Telegram-бота или Mini App | Проверь актуальные правила Telegram Stars; не подменяй обязательный маршрут внешней кассой |
| Нужен только подготовленный локальный пилот | Собери независимые части и проверки; не изображай реальные продажи |

Документация Telegram требует Stars для цифровых продаж внутри Telegram. Разделяй независимую продажу на сайте и продажу в интерфейсе Telegram; допустимость конкретного сочетания покупки/выдачи проверяй по действующим правилам. Не предлагай внешнюю кнопку как обход. Выбор ЮKassa/Prodamus сам по себе не определяет допустимость канала. Не превращай 990 ₽ в 990 XTR и не назначай курс автоматически: смену валюты/цены согласуй как изменение предложения, если пользователь её ещё не определил.

Перед кодом прочитай актуальную официальную документацию **выбранного** провайдера: формат запросов, создание заказа, подтверждение, подпись/проверка подлинности, повторы, тестирование, возврат. Запиши ссылки и дату в README/CHECKS. Без доступа к документации не выдумывай поля и алгоритмы; подготовь независимую часть и назови неподтверждённую интеграцию.

## Различия провайдеров

### ЮKassa

Используй текущие API/официальный серверный SDK. Shop ID и секретный ключ находятся на сервере; тестовые и боевые настройки разделены. Создание/повтор запроса выполняй с поддерживаемой провайдером идемпотентностью.

Не переноси на ЮKassa HMAC-схему Prodamus. В текущих рекомендациях подлинность уведомления проверяют, в частности, запросом актуального объекта API или IP. Для выдачи надёжно получи платёж через авторизованный серверный запрос и сопоставь его с заказом: итоговый успешный статус, сумму, валюту, магазин/связь с заказом. Сетевые ограничения добавляй по актуальным рекомендациям и устройству proxy, не доверяя произвольному клиентскому заголовку IP.

`waiting_for_capture` не равно завершённой покупке; не открывай товар по промежуточному состоянию. События `payment.succeeded`, `payment.canceled`, `refund.succeeded` обрабатывай с повторной проверкой актуального состояния. Учитывай связанные возвраты и сохранённое итоговое состояние права: повторная проверка успешности исходного платежа не отменяет подтверждённый возврат. Настрой HTTPS-уведомления по документации, не ориентируясь на возврат браузера покупателя.

### Prodamus

Используй платёжную страницу и текущую инструкцию самостоятельной интеграции. Товар, цена, количество и идентификатор заказа определяются доверенной стороной. Подписывай параметры там, где это требует выбранная интеграция; не позволяй посетителю поменять сумму и получить полный товар.

Проверяй подпись уведомления по официальной HMAC-библиотеке/актуальному алгоритму, включая канонизацию данных и заголовок `Sign`. Не заменяй это произвольным хешем от raw JSON и не игнорируй неподписанный запрос. После проверки сверь поля статуса и оплаты с локальным заказом по актуальной спецификации. Ошибка подписи прекращает выдачу.

Не предполагай существование универсальной sandbox-карты или тестового параметра. Доступный способ тестирования выясняй по документации/аккаунту пользователя; локальные подписанные фикстуры и собственный stub — имитация, а не подтверждённая оплата Prodamus. Демо-доступ при необходимости получает владелец аккаунта; не связывайся с поддержкой без его поручения.

### Другой провайдер или готовая платформа

Сохрани те же проверяемые свойства. Если платформа уже надёжно хранит заказы и закрывает выдачу, не дублируй её собственным магазином без необходимости. Проверяй фактические возможности интеграции, а не рекламное обещание сервиса.

## Минимальная надёжная модель

Разделяй состояния **платежа**, **права на товар** и **доставки**. Достаточно существующей платформы или небольшого постоянного хранилища. Перезапуск процесса не теряет покупку; для одиночного сервера может подойти SQLite на сохраняемом диске, для иных сред выбери подходящую БД.

Храни минимум: идентификатор заказа, товар/версию/тариф, сумму и валюту, защищённую связь с покупателем, идентификатор попытки/платежа, проверенный статус, предоставленное право и состояние выдачи. Персональные данные не добавляй без необходимости. Деньги обрабатывай без ошибок float.

1. Создай заказ с серверной ценой; повторное нажатие управляет попытками оплаты, не вызывает незаметное двойное списание.
2. Отправь на размещённую у провайдера оплату; данные карт сам не собирай.
3. Проверь уведомление и сверку заказа. Неполная/чужая сумма, валюта или подпись не дают доступ. Частичную оплату трактуй по явно выбранным условиям, не как полную по умолчанию.
4. Надёжно запиши подтверждение и однократно выдай право. Уникальность/транзакция защищают от параллельных повторов.
5. Зафиксируй задачу выдачи в постоянном состоянии; после устойчивой фиксации отвечай провайдеру в требуемом формате. Не теряй товар из-за сбоя между подтверждением платежа и отправкой.
6. При сбое доставки сохрани оплаченный заказ, покажи покупателю статус и восстановление. Выполняй ограниченный повтор без нового списания и повторного начисления пакета.
7. Повторное или позднее событие не возвращает подтверждённый возврат/закрытое право в старое состояние. При сомнении сверь актуальное состояние провайдера.

Не нужна сложная очередь ради одного продукта; нужна возможность восстановить незавершённую выдачу. Клиентский `paid=true`, письмо-скриншот и страница успеха не заменяют подтверждение провайдера.

## Получение и восстановление

**PDF:** существующий проверенный файл и защищённая загрузка, доступная нужному покупателю. Подойдёт выдача платформой или ограниченная/временная ссылка с проверяемым правом. Номер заказа сам по себе не является авторизацией. Истечение ссылки не уничтожает купленный доступ: предусмотрено безопасное повторное получение.

**Видео:** рабочее видео в подходящем закрытом хранилище/платформе, практика и материалы; согласованные срок и условия доступа. Проверь запуск и звук на телефоне. Платный файл не клади в публичный GitHub, public/static или общедоступный объект только потому, что ссылка не видна на лендинге.

**Приложение/бот:** серверные права, лимиты пакета или срок, разделение результатов, восстановление входа. Повтор webhook не начисляет дополнительные кредиты, повтор входа не запускает новую покупку. Не создавай сложный аккаунт, если для этого товара достаточно надёжной покупки/ссылки платформы.

**Telegram как канал выдачи:** пользователь должен начать диалог; привяжи покупку к аккаунту через проверенный одноразовый токен/код, а не доверяй ID из формы. При блокировке бота или недоступности Telegram оплаченный заказ сохраняется; дай восстановление через страницу заказа или согласованный резервный канал. Приглашение в закрытый канал должно выдавать именно обещанное право, с ограничениями, если они нужны. Не обещай защиту от копирования после скачивания.

**Возврат:** запрос и подтверждённый возврат — разные состояния. После подтверждения применяй выбранное правило доступа; частичный возврат требует отдельного правила. Уже скачанный файл нельзя «забрать обратно». Не выдумывай реквизиты, оферту и юридические условия продавца: запроси необходимые поля для настройки и оставь остальные заполнить владельцу. Чеки/налоговые параметры настраивай под реальный статус продавца по текущим требованиям провайдера, не обещая юридическую готовность автоматически.

## Приёмка покупки

| Проверка | Должно наблюдаться |
| --- | --- |
| Успех | Подтверждённый заказ → одно право → покупатель открывает именно приобретённый товар |
| Ожидание/отказ/отмена | Платный доступ не открывается, состояние понятно |
| Подделка/несовпадение | Чужой заказ, сумма, валюта, подпись или клиентский success не дают товар |
| Повтор/параллельный callback | Нет второго начисления, списания или новой покупки |
| Сбой/перезапуск между оплатой и выдачей | Оплата сохраняется; незавершённая выдача восстанавливается |
| Повторное получение | Возвращает купленный товар/остаток пакета без повторной оплаты |
| Другой покупатель | Подстановка идентификатора не открывает чужой товар/результат |
| Возврат и позднее событие успеха | Применяется правильное актуальное правило доступа |
| Реальный получатель | Файл скачан и открыт / видео воспроизведено / действие сервиса выполнено |

Проверяй только выбранный маршрут. Локальная имитация, тестовый платёж провайдера, боевой платёж, ответ доставки API и фактическое получение — отдельные свидетельства. Боевой проверочный платёж/возврат с расходами выполняй только в уже разрешённом объёме; иначе предложи владельцу конкретный тест. Секреты не публикуй в чате, клиентском коде и логах; дай названия env-переменных и место безопасного ввода.
