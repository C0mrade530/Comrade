# GitHub, хостинг и проверка запуска

Читай, когда продукт нужно загрузить в репозиторий, развернуть или проверить после публикации. Публикация кода и работающий продаваемый продукт — отдельные этапы.

## Узнай назначение без лишних вопросов

Из контекста, Git remote и доступных подключений определи точный `owner/repository`, рабочую папку, ветку, существующий хостинг, домен и способ выпуска. Имя репозитория без владельца может быть неоднозначным. Если источник не даёт ответа, запроси ссылку; не создавай одноимённый репозиторий и не выбирай чужой автоматически.

Перед изменениями прочитай инструкции проекта, структуру, конфигурацию сборки/запуска и текущие workflow. Сохрани пользовательские изменения. Не загружай весь рабочий стол или весь каталог с исследованиями. В репозиторий идут только файлы выбранного продукта/skill; секреты, данные покупателей, закрытые товары, виртуальные окружения и локальные артефакты туда не попадают.

Новый функционал добавляй отдельной веткой `codex/<понятное-имя>` и PR, если пользователь не выбрал иной порядок. Не выполняй force push, не перезаписывай main и не меняй existing workflow ради удобства. Созданный PR прикрепляй к текущей задаче, если такая возможность доступна.

Внешние действия выполняй в уже порученном объёме. «Как устроишь деплой?» — вопрос о процессе, а не автоматическое поручение изменить репозиторий. «Выложи в этот репозиторий и опубликуй» — поручение сделать согласованные шаги без повторных вопросов. Не создавай новый платный аккаунт/сервер или домен без соответствующего решения пользователя.

## Выбери подходящую архитектуру

| Что запускаем | Что требуется |
| --- | --- |
| PDF или записанный урок | Хранилище/платформа с доступом и выдачей; при необходимости лендинг и платёжная интеграция |
| Статический интерфейс коммерческого продукта | Подходящий коммерческий хостинг; закрытая выдача/оплата отдельно либо встроены в платформу |
| Сайт с сервером | Совместимый runtime, env, HTTPS, постоянная БД/хранилище и обработчик уведомлений |
| Telegram-бот | Среда с поддержкой нужного режима webhook/long polling, хранения и восстановления после рестарта |

GitHub хранит исходники и может запускать workflow. GitHub Actions не используй как постоянный сервер бота или БД. GitHub Pages обслуживает статические сайты и имеет ограничения на коммерческие магазины/SaaS; для этой ветки выбирай другой подходящий хостинг. Не делай платный PDF/видео общедоступными через Pages или открытый release.

Предпочти уже используемый хостинг, если он подходит. Иначе предложи один простой вариант с объяснением ограничений, доступов и расходов. Не обещай бессрочный бесплатный тариф, объём ресурсов и возможность callback без проверки текущих условий поставщика. Для serverless не рассчитывай на локальный диск как постоянную БД и на бесконечный процесс. Для VPS/контейнера обеспечь сохранность данных, автозапуск и понятный restart.

## Подготовь конкретный выпуск

Собери минимально нужное для выбранной среды:

- команды установки, сборки и запуска, проверенные локально;
- lockfile/зафиксированные нужные зависимости и `.env.example` без значений секретов;
- исключение env, пользовательских данных и закрытых товаров из публикации;
- настройки runtime/контейнера/процесса, только если среда их требует;
- хранение заказов/прав и резервную копию, если они есть;
- HTTPS-адреса сайта, webhook и возврата с оплаты;
- выпуск версии, способ проверить состояние и восстановить предыдущую.

Секреты передавай через защищённые настройки хостинга/CI. Не печатай содержимое env и не вкладывай ключи в GitHub workflow. Не проси менять биллинг, ограничения Actions и security-настройки, когда можно использовать уже разрешённый путь. Недоступные hosted checks отмечай недоступными; локальные проверки их не превращают в зелёные.

Если выбранный репозиторий уже автоматически выкладывается по push/merge, сначала учти этот эффект. Не запускай production-выпуск случайно изменением ветки, если разрешён только просмотр/подготовка. При существующей авторизации выполняй нужный выпуск, сохраняя откат и данные.

## После выкладки

1. Зафиксируй фактический commit/версию, среду и живой URL.
2. Открой URL и пройди основной путь. HTTP 200 и зелёный build не заменяют работающую функцию.
3. Для покупки проверь актуальные адреса уведомлений, доступный тестовый платёж и выдачу после него. Для бота проверь запуск и выбранный пользовательский путь.
4. Проверь восстановление доступа и сохранение покупки/лимитов после допустимого рестарта; не перезапускай чужую production без основания в задаче.
5. Передай владельцу конкретные команды/настройки: где обновить товар, цену, env, увидеть невыданный заказ, повторить выдачу, откатить выпуск и обратиться за поддержкой.

Отдельные статусы: код загружен → билд выполнен → приложение доступно → проверено по URL → провайдер подтвердил оплату → товар выдан → покупатель открыл/использовал. Если доступа к хостингу нет, закончи код/конфигурацию/инструкцию и назови конкретные недостающие действия; не выдумывай адрес опубликованного сайта.

Источники: [GitHub — Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [ограничения Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits). Специфику выбранного хостинга проверяй по его актуальной документации.
